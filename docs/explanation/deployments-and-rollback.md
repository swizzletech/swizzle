# Deployments, rollback and retention

A deployment is one activation of an automation in one environment. History is append-only: a deploy and a rollback both add a deployment, and neither changes an old one. That rule keeps every run traceable to the exact code and configuration it ran, and it decides how rollback and retention work.

## A deploy adds a version and a deployment

[`commitDeployment`](../../packages/db/src/control-plane-deployments.ts) runs in one transaction under a lock on the automation row:

1. It finds or inserts the version ([`automationVersions`](../../packages/db/src/schema.ts)), identified by the `version` label, the source hash and the config hash together. The label alone identifies nothing, because two deploys can carry the same label with different code.
2. It marks the active deployment of that environment `inactive` and inserts a new active one ([`deployments`](../../packages/db/src/schema.ts)) with the next `seq`. The sequence counts per automation across all environments, so `#7` names one deployment.
3. It builds the trigger input with [`buildDeploymentTriggerInput`](../../packages/db/src/deployment-trigger-input.ts), syncs that input to the new deployment, and writes a deployment audit event. The PostgreSQL store and deployment preview use the same builder for cron, every, webhook, and chain triggers. Chain sources need active deployments in the consumer's project and environment. A missing source and a source in another project both refuse deployment with `TRIGGER_CONFIGURATION_INVALID` and `Chain source automation not found: <name>`, even when the deployer can read both projects. The runtime checks sources before creating artifacts. The transaction checks again before publishing the config. A chain source cannot be the target automation or one of its downstream automations, because either choice would create a cycle.

Each deployment artifact records the binary version matching rule used by readiness. Older artifacts have no rule field, so runs, API checks, and worker image preparation use the 1.0.4 matcher for them. That matcher accepts `latest` when a worker reports a version because the rule has no numeric components. New source rejects `latest` and records numeric-prefix matching, where bare `25` matches `25.3`. Keeping the rule in the artifact lets an upgrade change validation for new deployments without changing readiness for installed ones.

Each deployment records the artifact locator, the runtime snapshot and the dependency build snapshot, so a later run of that deployment knows which tree and which runtime it needs. A run row references its deployment and its version. Those foreign keys use `onDelete: "restrict"` ([`runs`](../../packages/db/src/schema.ts)), so PostgreSQL refuses to delete a deployment or version that any run used.

Deployment readiness reads the worker registry, where each worker's row holds its grants, liveness and the capabilities its last heartbeat measured. Deploy and rollback load one worker snapshot before committing and reuse it in the response. A registered group whose workers sleep allows deployment with a warning. An unknown group or a failed registry query stops the operation before commit.

Before building, a deploy passes [`checkDeployment`](../../packages/runtime/src/deployment-check.ts). The check covers the source hash, webhook path, project placement, chain sources, credential use, and readiness. `POST /deployment-checks` runs the same check without building, so `swizzle validate` and `swizzle apply --dry-run` report the deployment result. The check changes nothing, so it writes no audit event and adds nothing to the automation's change history. Dry-run and remote validation print the check's action and changed fields. Apply reports the transaction's action and uses the same comparison against the deployment that transaction replaced. A concurrent apply therefore cannot leave its reported previous values stale; a committed no-op has no changes. Clients do not compare against a separately fetched deployment. A claimed webhook path returns `TRIGGER_WEBHOOK_PATH_CONFLICT` during preflight. The commit also returns that code if two deployments pass preflight together and PostgreSQL rejects one trigger insert for a duplicate webhook path. The database error may be wrapped, so `commitDeployment` checks its `Error.cause` chain for the `automation_triggers_webhook_path_unique` violation. A deployment fails with `RUNTIME_REQUIREMENTS_UNMET` when workers are not ready, unless `--force` skips that check.

`swizzle apply` sends the source hash it computed from the bundle's files. [`checkDeployment`](../../packages/runtime/src/deployment-check.ts) hashes the extracted files before anything is stored. If the hashes differ, the API returns `DEPLOYMENT_CONTENT_HASH_MISMATCH` before the deployment transaction, leaving the active deployment unchanged.

A deploy with the same source hash, config, and credential bindings as the active deployment changes nothing and reports `no source or config change`. Replacing a deleted credential changes its binding and requires a new deployment even when the source and config match. `swizzle apply --force` also deploys unchanged content. The preflight check and the locked transaction use the same source and config comparison from [deployment-comparison.ts](../../packages/db/src/deployment-comparison.ts), so a deployment committed during the build follows the same content rule. The runtime checks credential bindings separately and passes `redeploy-if-unchanged` to the store when force or changed bindings require a new deployment.

## A worker prepares a deployment before its first run

The run image holds the automation source and installed dependencies. The API cannot access Docker by design. Each worker prepares active deployments for its profiles ([`startDeploymentPreparation`](../../packages/runtime/src/deployment-preparation.ts)). The API sends immutable source bundles for the worker's approved project/environment and profiles, without storage credentials or secrets. A worker reuses the image on its Docker engine when the deployment's tag already exists. If the deployment is less than ten minutes old, the worker also starts a standby sandbox ([the security model](security-model.md#a-run-gets-only-what-it-declared)).

`swizzle apply` returns before workers finish preparation. A run that starts during image assembly reports `phase: "preparing"` on its active execution, and the run panel says **Preparing**. The phase changes to `executing` after image and sandbox preparation, when the process timeout starts. The run joins an assembly already in progress. Each joining run receives the assembly's earlier logs and its new output, including reassembly notices. If preparation fails or has not finished, the first run assembles the image. Before assembly, the worker records the deployment's tag in PostgreSQL, so pruning can keep the image if assembly fails or the worker restarts.

Each worker process prepares its own deployments. Run image tags name the source, recipe, stack and architecture, not the worker, so a recreated worker container and replicas that share a Docker engine reuse one image. One process assembles it while the others wait, and a tag that exists never moves. A rollback creates a new deployment and goes through preparation again. Its image can reuse an existing image when the source and recipe match. The worker reports each deployment's image tag to the API before assembly. PostgreSQL keeps that deployment and worker association across restarts. Before it prunes, a worker asks the API for its keep set: the latest image it reported for each active version, including while an identical-source replacement is being prepared. The keep set belongs to the worker's credential, and every worker container of a stack shares one, so the replicas that share a Docker engine keep the same images. No lock spans the pass; the [security model](security-model.md#a-run-gets-only-what-it-declared) names the one race left between replicas. Active deployment images remain even when their total exceeds the disk budget. The [security model](security-model.md#a-run-gets-only-what-it-declared) explains which images the budget covers and how Settings > Workers reports an overage. A replaced deployment's image stays while it remains within the retention window and the disk budget has room. A rollback soon after a deploy usually finds it.

## Rollback creates a new deployment

`swizzle rollback <automation> <deployment>` takes the target as a deployment id or as `#<seq>` ([`resolveDeploymentTarget`](../../apps/api/src/automation-routes.ts)). The target must be a deployment of that automation in the same environment. It does not move a pointer back. [`commitRollbackDeployment`](../../packages/db/src/control-plane-deployments.ts) copies the target into a new active deployment with the next `seq` ([`buildRollbackDeployment`](../../packages/db/src/control-plane-deployments.ts)), so the history reads in the order things happened: `#5` deployed, `#6` deployed, `#7` rolled back to the code of `#5`. Runs of `#6` keep pointing at `#6`.

A rollback is a deploy of old code, so it goes through the same checks:

- [`performRollback`](../../packages/runtime/src/deployment-admin.ts) first checks that the target's artifacts still exist ([`validateArtifactExists`](../../packages/runtime/src/deployment-admin.ts)). A target whose tree retention deleted fails before anything changes.
- It syncs the trigger exactly like a deploy. A webhook path that another automation took in the meantime fails the rollback with `ROLLBACK_CONFLICT`. A cron trigger follows the new deployment, because the scheduler reads triggers from PostgreSQL.
- It writes an audit event of type `rollback` with the target id.

## Deleting a source leaves its chains invalid

Deleting an automation removes its deployments and runs in every environment, while its audit events stay. The CLI names dependent chains before asking for `--yes`, including paused chains in other environments. If the API cannot preview that impact, the CLI refuses to delete. A dependent keeps an invalid trigger with `TRIGGER_CHAIN_SOURCE_DELETED`, so `swizzle inspect` and the dashboard show which source was deleted and mark the dependent not ready. Restore the source, then run `swizzle apply <dependent-dir> --force`, or change the dependent's trigger and deploy it. A join cannot resume with fewer sources than it declared.

## Retention expires finished runs and bounds bulk

The scheduler's maintenance cycle ([`runMaintenanceCycle`](../../packages/runtime/src/maintenance.ts)) bounds what grows without limit. Each environment's pass expires only its own runs, so concurrent passes do not sweep the same history. Each setting is an environment variable read by [`resolveMaintenanceRetentionPolicy`](../../packages/runtime/src/maintenance.ts):

| Data | Retention rule | Variable | Default |
|---|---|---|---|
| Finished runs with their attempts, logs, step values and webhook request context | days after the run finished | `SWIZZLE_RUN_RETENTION_DAYS` | 30, `off` keeps them |
| Service heartbeats | hours | `SWIZZLE_HEARTBEAT_RETENTION_HOURS` | 6 |
| Notification deliveries | days | `SWIZZLE_NOTIFICATION_DELIVERY_RETENTION_DAYS` | 30 |
| Queue metric samples | days | `SWIZZLE_QUEUE_METRIC_RETENTION_DAYS` | 14 |
| Failed BullMQ jobs | hours | `SWIZZLE_QUEUE_FAILED_RETENTION_HOURS` | 24 |
| Deployment artifact trees | the active deployment plus the newest N per automation | `SWIZZLE_ARTIFACT_RETENTION_DEPLOYMENTS` | 5, `off` keeps them |

The table names everything the cycle deletes. A run that succeeded, failed or was dead-lettered expires as a whole once it finished longer ago than the retention age ([`expireRuns`](../../packages/db/src/control-plane-maintenance.ts)). Queued, running and waiting runs never expire, however old. A child run whose parent expired keeps running and loses its parent link. Audit events stay, and so do deployments and versions. Accepted cron ticks, webhook deliveries, and chain hops live in run history: the run stores their trigger type, payload, and chain source IDs, and retention deletes them with the run. The audit log keeps trigger configuration changes and refused requests. An expired deployment's row stays. The sweep ([`sweepDeploymentArtifacts`](../../packages/runtime/src/maintenance.ts)) deletes its artifact tree only when no retained deployment uses that tree. A rollback deployment runs from its target's tree, so retention keeps that tree even when the deployment that wrote it falls outside the newest N. A rollback to an expired deployment can therefore pass the artifact check while a retained deployment shares its tree.
