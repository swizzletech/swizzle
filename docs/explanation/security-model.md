# The security model

Swizzle is designed for one self-hosted instance shared by several people. Instance roles and project grants control access for people, teams, and service accounts. Better Auth handles sign-in, sessions, and two-factor sign-in with the guarantees below. Setup creates the first account as the instance owner. After that, only an invitation can open an account. One policy decides what each person may see and change in a project and environment. Every unauthenticated route has a named exception and its own guard. Automation code runs with the least authority the platform can give it. Multi-tenant hosting is out of scope.

## Accounts and two kinds of credential

Sign-in runs on [Better Auth](https://better-auth.com) 1.7.12, pinned to the exact version, with its Drizzle adapter and two-factor plugin ([`auth.ts`](../../packages/db/src/auth.ts)). The API forwards only the Better Auth routes listed in [`auth-routes.ts`](../../apps/api/src/auth-routes.ts) and answers every other `/auth/*` route itself. Better Auth's own rate limiter, account lockout and trusted devices are off; Swizzle's guarantees below replace them.

The auth boundary translates Better Auth failures into public Swizzle codes and messages. For an unmapped failure below HTTP 500, it returns `AUTH_REQUEST_INVALID`. For an unmapped failure at HTTP 500 or above, it returns `AUTH_REQUEST_FAILED`. The API forwards the code and message, and the shared error handler sets the HTTP status from the code. Clients do not need to interpret Better Auth codes. For sign-in and two-factor enrollment, [`auth.ts`](../../packages/db/src/auth.ts) parses Better Auth's successful JSON into `SignInResult` and `TwoFactorEnrollment` from [`auth-types.ts`](../../packages/db/src/auth-types.ts). The other forwarded actions return only Swizzle's `{ success: true }` acknowledgment. The auth boundary discards Better Auth's success JSON. No forwarded route exposes the library's user object. The API contract uses these Swizzle types. If Better Auth returns a body the auth boundary cannot read, the API answers `AUTH_REQUEST_FAILED`. Cookies and `Retry-After` travel in headers, outside the JSON result.

A fresh instance shows a setup form. When `SWIZZLE_SETUP_TOKEN` is configured, setup requires that token. Setup creates the first account. Once that account exists, sign-up without an invitation answers `403 AUTH_INVITATION_REQUIRED`. The account insert claims setup in the same transaction, so two simultaneous setups create one account. Passwords are 15 to 128 characters and use salted scrypt hashes with `N=32768`, `r=8`, and `p=3`. Sign-in hashes a password for an unknown email too, so response time does not reveal whether an account exists.

A person holds two kinds of credential, and both are stored only as SHA-256 hashes:

- A dashboard session is an `HttpOnly`, `SameSite=Lax` cookie with a 7-day absolute limit and a 30-minute idle limit by default. `SWIZZLE_SESSION_IDLE_TIMEOUT_MINUTES` sets the idle limit from 5 to 1440 minutes. The cookie is `Secure` and uses the `__Secure-` prefix when `SWIZZLE_AUTH_COOKIE_SECURE` is true, or when it is unset and an allowed dashboard origin uses HTTPS. In production, the API refuses a false setting when a public HTTPS origin is configured ([`security-config.ts`](../../apps/api/src/security-config.ts)). The account page labels each session with the browser and device parsed from its saved user agent. A person can use the label to choose which session to revoke.
- A bearer token is for the CLI and agents. A person mints it in **Settings → Agent access**, can limit its scope there, and sees the plaintext once. Every token expires, after 90 days by default and after at most 366 ([`api-tokens.ts`](../../packages/db/src/api-tokens.ts)). One token per device keeps revocation precise. The API updates a token's last-use time at most once per minute. The dashboard can show a time up to one minute old. A token acts as a person or as a project's service account, never beyond the scope fixed when it was minted ([tokens act within a fixed scope](#tokens-act-within-a-fixed-scope)). A token cannot administer accounts, change passwords, manage sessions or tokens, or change two-factor sign-in. The API answers `403 AUTH_SESSION_REQUIRED` for those requests.

### Worker credentials

Workers have their own actor type, separate from personal tokens and project service accounts.
An owner or instance admin grants each worker the Project and environment pairs it may serve, plus its allowed runtime profiles.
Worker credentials authorize worker protocol routes only. The packaged local credential is accepted only on a separate listener bound to the private Compose worker network; public ingress rejects it on authenticated routes. Public endpoints ignore bearer headers. Settings marks that identity as Local and an owner can revoke it.
The [worker protocol](../reference/worker-protocol.md) defines enrollment, token lifetime, enrollment budgets, revocation, and audit behavior.

### People: invitations, roles, suspension and removal

`GET /users` and `GET /teams` require an owner or admin with a browser session or a full-scope personal token. The people list includes instance roles, suspension, and two-factor state. Sharing and assignment pickers use `GET /directory?environment=<name>` instead. It returns only each person's id, name, and email, and each team's id and name. For members and service accounts, candidates belong to projects their grants and token scope expose in that environment, including direct automation shares. Active owners and admins also appear because they can access those projects. Suspended people are excluded. A caller with no visible project gets an empty directory. A project's access list (`GET /projects/:project/access`, for its admins) names the instance role only of owners and admins, as the reason they reach the project. It shows no instance role for anyone whose access comes from grants ([`access-holders.ts`](../../packages/db/src/access-holders.ts)).

Every account has an instance role: `owner`, `admin` or `member`. Owners and admins manage people in **Settings → People** and through the `/users` and `/invitations` routes ([`people-routes.ts`](../../apps/api/src/people-routes.ts)). Only an owner may change an owner, assign the owner role, or invite or revoke an owner ([`mayManagePeople`](../../packages/db/src/access.ts)). Other attempts answer `403 ACCESS_DENIED`. There can be several owners. The last active owner cannot be demoted, suspended, or removed. Those attempts answer `409 AUTH_LAST_OWNER`. Every change to a person uses typed database queries in a transaction with an advisory lock shared by account management, including when no owner row exists. It checks the actor's and target's current roles before writing. If two owners demote each other at once, one owner remains. If an owner promotes a target while an admin's change waits, the API refuses the admin's change ([`auth-membership.ts`](../../packages/db/src/auth-membership.ts)).

Each invitation stores an email address, an instance role, and optional project grants. Swizzle stores invitations in its own table, and PostgreSQL holds only the token's SHA-256 hash. `POST /invitations` answers with the link `SWIZZLE_DASHBOARD_ORIGIN/invitation#<token>` once, for the inviter to pass on, and the API also mails it when `SWIZZLE_SMTP_URL` is set. Whoever holds the link can create the invited account, so treat it as a password until it is used. A Better Auth plugin accepts sign-up only when a pending invitation's token matches the submitted email. The link expires after 7 days and can create one account. A new invitation to the same address replaces the earlier link, even when two requests race. An owner or admin can revoke a pending invitation.

On the invitation page, the person sets a name and password. The account insert claims the invitation in the same transaction. It leaves the email unverified, because the inviter may have passed the link on by hand. Swizzle activates project grants after the account commits. Each grant and its activation marker commit together. If grant activation fails, the next sign-in retries only grants that remain pending. It does not restore a grant an admin removed later.

Nodemailer handles SMTP and message formatting. In the Compose stack, its transport uses the control egress proxy ([`mail.ts`](../../packages/core/src/mail.ts)). For `smtp://`, Swizzle requires STARTTLS unless the server is on loopback. For `smtps://`, the connection starts with TLS. A mail server rejection fails the invitation with `502 AUTH_MAIL_FAILED`, and Swizzle stores nothing.

Suspending a person ends their sessions at once. Their API tokens are refused on the next request with `403 AUTH_ACCOUNT_SUSPENDED`, which tells them to ask an owner or admin. Sign-in with their correct password answers `403 AUTH_ACCOUNT_SUSPENDED`; a wrong password answers as for anyone. Reactivation restores sign-in and the same tokens. Removing a person deletes their account, sessions, tokens, grants, team memberships and pending invitations. Automations, runs and audit events they created stay.

Password and second-factor recovery use four paths:

- A forgotten password: when mail is configured, the sign-in form offers a reset link. The link works once for an hour, and Better Auth stores only a hash of its token. A reset ends every session and revokes every API token of the account. A used, expired, or unknown link answers `400 AUTH_RESET_LINK_INVALID`. The reset page tells the person to ask for a new link on the sign-in page or from an owner or admin. A reset request gives the same response for an unknown address.
- A forgotten password, handed over: an owner or admin creates a reset link for another person in **Settings → People** or with `swizzle people reset-link <email>`. Both methods work without mail (`POST /users/:userId/reset-link`). The API shows the link once, to the person who asked. The audit records who created it for whom, without the token. Using the link ends all of that person's sessions and revokes their API tokens. An admin cannot create a link for an owner, and nobody can create one for themselves. To change a password while signed in, a person uses **Settings → Account** and enters the current password.
- A lost second factor: an owner or admin turns it off for the person, which ends that person's sessions. The person then signs in with the password and can set up the factor again.
- A locked-out owner: someone with shell access to the host runs `just recover-owner <email>` ([recover a locked-out owner](../how-to/install.md#recover-a-locked-out-owner)). The command runs [`recover-owner.ts`](../../apps/api/src/recover-owner.ts) in the API container. It turns off the owner's second factor, ends every session, and prints a reset link. The link works once for an hour and revokes the owner's API tokens when used. The command prints no secret other than the reset link.

The command records an audit event with actor kind `host` before it changes the account. It also records an event when the address names no active owner. No API route can start recovery. The API server builds `SwizzleAuth`, while the command alone builds `HostAuth` ([`auth.ts`](../../packages/db/src/auth.ts)).

### What Swizzle adds to Better Auth

Better Auth handles sign-in, sessions, and TOTP checks. Swizzle enforces four guarantees: hashed session tokens, idle and absolute session limits, single-use TOTP codes, and persistent sign-in budgets. Swizzle applies them through its database adapter and plugin. The same checks run with the PostgreSQL adapter in production and tests:

- **Hashes at rest.** The session table holds SHA-256 of each token, never the token ([`auth-session-store.ts`](../../packages/db/src/auth-session-store.ts)). A lookup hashes the cookie's token first, so a value read from the table and presented as a cookie, even correctly signed, finds no session. No response body carries a session token; the cookie is its only carrier.
- **Idle and absolute limits.** By default, a session ends 30 minutes after it was last seen and 7 days after sign-in. To avoid a database write on every request, the row's last-seen time moves only when it is older than a tenth of the idle limit. A session can then end up to that interval earlier, never later. The lookup reads both limits from the row, so an expired row cannot open a session even before cleanup deletes it. Better Auth replaces a session when two-factor sign-in changes; the replacement keeps the first sign-in's end time.
- **Each TOTP code once.** Better Auth verifies the code. Swizzle reserves a hash of the person and code in PostgreSQL before verification, and never stores the code itself. A unique index lets one of two simultaneous requests continue. Failed checks release their reservation. A successful reservation remains through the full validity window, at most 90 seconds, and the next TOTP attempt deletes expired reservations. Unused codes from any step in Better Auth's validity window work, even after a code from a later step ([`auth-two-factor.ts`](../../packages/db/src/auth-two-factor.ts)).
- **Persistent budgets.** Sign-in and worker enrollment spend separate keys in the same PostgreSQL fixed window counter ([`budgets.ts`](../../packages/db/src/budgets.ts)). Restarting the API does not reset them. See below.

### Two-factor sign-in

Two-factor sign-in is optional for every role. No setting enforces it. Setup and invitation acceptance offer it as the default, but the person may skip it. A person can also turn it on later in **Settings → Two-factor sign-in**. The password starts setup, and the dashboard shows an RFC 6238 QR code. An authenticator app supplies the code that finishes setup. Better Auth uses HMAC-SHA1, six digits, and 30-second steps. It accepts codes from the current step and the step before or after it. Setup returns ten recovery codes once. Each code signs in once in place of a TOTP code.

While the factor is on, sign-in has two steps. `POST /auth/sign-in/email` with the right password answers `{ "twoFactorRedirect": true }`, sets a short-lived challenge cookie and opens no session. `POST /auth/two-factor/verify-totp` with a code, or `POST /auth/two-factor/verify-backup-code` with a recovery code, then opens the session. No browser is ever trusted to skip the code.

Turning the factor off needs the password and a TOTP or recovery code. Turning it on or off signs out every other browser. While the factor is on, a password change needs a TOTP or recovery code as well as the current password, so a stolen session cannot replace the password. Better Auth checks each password once. After a successful password check, Swizzle asks Better Auth to verify the TOTP or recovery code before changing credentials. An invalid password or new password length leaves the code unused. A password change signs out every other browser and keeps the one that made it. Agent tokens are not sign-in and keep working.

The secret and the recovery codes are encrypted under a key derived from `SWIZZLE_ENCRYPTION_KEY`, and `just db-reencrypt` rewrites both during [key rotation](../how-to/rotate-the-encryption-key.md). After setup, the API never returns either.

### Sign-in budgets and the device rule

Each budgeted request spends its budget before Better Auth validates the body, so a malformed attempt costs the same as a wrong one. A password change from a signed-in session spends the same password budget as sign-in, and a code there spends the code budget, so a stolen session cannot guess faster than sign-in allows:

| Budget | Limit | Key |
|---|---|---|
| Address | 30 attempts per minute | The client address |
| Password | 5 attempts per minute | The account, or the device |
| Code | 5 codes per 15 minutes | The account, or the device |
| Sign-up | 10 attempts per 5 minutes | The client address |
| Reset mail | 3 mails per 15 minutes | The email address |

A per-account budget alone would let anyone who knows a person's email lock them out with wrong passwords. After setup or a sign-in, the browser keeps a `swizzle.device` cookie that holds a random `HttpOnly` token, and the database stores its SHA-256 hash. A browser that signed in to this account before spends its own password and code budgets and skips the shared address and account budgets, so an attacker using another browser cannot exhaust them. A device of another account counts as no device.

The code budget also limits guesses against the second factor. Five codes per 15 minutes allow 480 attempts per day, so someone with the password has about a 0.14% chance per day of guessing a six-digit code within one budget scope.

A browser write must come from an allowed page. The API answers `403 AUTH_ORIGIN_FORBIDDEN` to a `POST`, `PUT`, `PATCH` or `DELETE` whose `Origin` header names a page outside `SWIZZLE_CORS_ORIGINS`, or outside `SWIZZLE_DASHBOARD_ORIGIN` when that is unset. The check runs before the API reads a credential, so it holds for a bearer token too. A write with a session cookie must also carry an allowed `Origin`. The CLI sends no `Origin` and passes.

The API sets security headers on the raw response when each request arrives, so routes that write past Fastify hooks still carry them ([`server.ts`](../../apps/api/src/server.ts)). The live log stream uses Fastify's response path, which preserves CORS headers and lets an origin in `SWIZZLE_CORS_ORIGINS` read the stream. It sends stored output and status before subscribing to Valkey, so a client gets the current state while Valkey is down. After subscribing, it reads the run again and closes the stream if the run ended during setup.

## One policy decides access

[`access.ts`](../../packages/db/src/access.ts) applies it to automation, run, and project requests. Project roles are `viewer`, `operator`, `editor`, and `admin`, in increasing authority. Automation and environment grants stop at `editor`.

| Role | Allows |
|---|---|
| `viewer` | Read automations, runs, logs and results |
| `operator` | Also start and cancel runs and send run events |
| `editor` | Also deploy, roll back, pause or resume triggers, write state, create secrets and connections, manage folders, and delete an automation |
| `admin` | Also grant roles, protect environments, share automations and move an automation to another project |

Every grant can name a person or a Team. An automation grant applies to one automation and does not reveal the rest of its project. When several project or automation grants apply, the highest role wins. A protected environment caps that role at the highest matching environment grant. Without an environment grant, a non-admin has no access there, while a project admin keeps admin access. An environment grant exists only in a protected environment: a grant in an unprotected one answers `409 ENVIRONMENT_NOT_PROTECTED` and names protecting it as the next step, and unprotecting an environment removes its grants ([`access-tables.ts`](../../packages/db/src/access-tables.ts)).

Setup grants the team `Release` access to production by default. A production grant does not give access to project content. A member needs both a project role and a production grant to change production. Owners and project admins keep their access without a production grant. See [how to add people who may release](../how-to/give-people-access.md#add-people-who-may-release) for the setup steps.

Deleting an automation requires editor access in every protected environment because deletion removes it from all environments. Every path that changes an environment checks that environment: deploy, rollback, pause, resume, and writing or deleting a secret or a connection.

Each automation belongs to one Project. New instances create the `default` project. A new automation joins it unless `swizzle apply --project <slug>` names another project. A deployment that names a different project fails with `409 AUTOMATION_PROJECT_MISMATCH`, because deploying never moves an automation. `swizzle move <slug> --project <project>` moves it and needs admin in both projects. Its triggers must be paused first, and the move removes its automation shares and its folder. A chain source or consumer cannot move alone while it is connected to automations that stay behind (`409 AUTOMATION_CHAIN_CONNECTED`). The refusal names the connected automations the caller may read. Remove the chain first, or move the whole project's contents together, so every chain stays within one project. A move into the project it is already in changes nothing and answers `moved: false`.

A chain trigger can name sources only in the consumer's project. This keeps deployment from revealing whether an automation exists in a project the deployer cannot read, and keeps source run results within that project.

History stays in the project where it was written. Runs and automation audit events keep that project when an automation moves, so earlier rows stay in the old project's run list and change feed. An automation share reaches rows for that automation in its current project only. The automation page, step counts, diagnosis and audit lists follow the same rule.

`swizzle delete` deletes the automation with its deployments, triggers, state and every run in every project, and frees its name. It refuses while a trigger is active or a run is unfinished. A chain trigger of another automation that names it as a source is removed with it, so that automation never waits for a source that cannot run again. Its audit events stay.

Deleting a project moves its automations, credentials and runs to another project, or deletes them with the project ([`deleteProject`](../../packages/db/src/control-plane-automations.ts)). The [project deletion guide](../how-to/give-people-access.md#delete-a-project) covers the dashboard choices. The API takes them on `DELETE /projects/:project`:

- `contents=move&to=<project>` moves them to a project the caller also administers. Automations lose their folder and keep their credential bindings, and the runs written in the project move too. A secret or connection name the target already uses in that environment refuses the move with `409 CREDENTIAL_NAME_CONFLICT`. A credential share between the two projects ends, since the credential now lives where it was accepted. A share a third project offered ends with the deleted project, so that project's admins offer it to the target again.
- `contents=delete` deletes the automations with their runs and the credentials, and revokes each connection at its provider. It refuses while a run is unfinished (`409 AUTOMATION_RUNS_ACTIVE`).
- Without `contents` only an empty project goes. Otherwise the API answers `409 PROJECT_NOT_EMPTY` with the counts that `GET /projects/:project/contents` also returns.

Either way the project's grants, service accounts, folders and protected environments go with it, and its audit events stay. The delete's own event records the choice in `details`: `contents`, and `to` for a move. The default project cannot be deleted (`409 PROJECT_PROTECTED`).

The API assigns every route a rule in [`ROUTE_ACCESS`](../../packages/runtime/src/http-contract.ts). A route is public, signed-in, instance-only, or resource-scoped. The API refuses to start if a route has no rule. With authentication enabled, an instance-only route requires an owner or admin. A resource route must check the named automation, run, or project through `request.access`; otherwise the API fails the response with `500`. The [API reference](../reference/api.md) lists the route rules.

`GET /projects/:project/worker-groups` requires project read access. It returns group names, machine names, and machine state. It returns no address or credential. A project reader can choose a `runtime.profile` from the list. Only an owner or instance admin can enroll or manage workers.

The API resolves a resource's project from its stored record, not from an ID supplied by the caller. Unknown resources and resources outside a person's grants both answer `404`. A visible resource that needs a higher role answers `403 ACCESS_DENIED`. The same `404` response prevents another project's IDs from revealing whether its resources exist. List queries apply the same scope in SQL, including counts and the change feed, so hidden runs do not affect visible totals ([`dashboard-shared.ts`](../../packages/db/src/dashboard-shared.ts)). Dashboard reads of deployment README and Mermaid files first check access to the automation. Run detail, logs and log streams check the run's stored project. A live log stream checks access again every 15 seconds. An automation's last run comes from the environment being viewed. A chain trigger names only the sources its reader may read and counts the rest, because a share of one consumer does not grant access to its sources in the same project ([`chainSourcesInScope`](../../packages/db/src/dashboard-shared.ts)). A member's overview omits platform and notification health. Automation slugs stay unique across projects, so a deployment can reveal that a hidden name is taken with `409`.

Project, automation and environment roles share one grant table. Worker execution grants use separate rows with project foreign keys, so deleting a project removes its worker grants. Credential rights remain separate because they grant use or management rather than a project role.

The API reads grants once per request, so a revocation applies to the next request. A live log stream reloads the person's instance role and grants every 15 seconds, checks that its token is still live, and ends when either is gone.

Automation folders belong to one project. Creating, renaming, deleting or assigning a folder needs editor in that project.

Owners and admins can see every project and manage instance resources, including people, teams, metrics, and security audits. Members see only projects their grants expose.

The sharing dialog shows every source of a person's project and environment roles. Removing one grant may leave another source of access.

## Tokens act within a fixed scope

A token has one of three holders ([`token-routes.ts`](../../apps/api/src/token-routes.ts)):

- A **personal token** acts as the person who minted it, with their instance role and grants as the API reads them on each request. Leaving a team, losing a grant, a demotion or a suspension limits the token on its next request. Removing the person deletes their tokens.
- A **service account token** acts as a service account. A project admin creates the account on the project's **Service accounts** tab, with `swizzle service-accounts create`, or with `POST /projects/<project>/service-accounts` and grants it project or credential rights through the `serviceAccount` grant subject. A service account can hold up to `editor`, never `admin`. Its token keeps working if the person who created the account or minted the token leaves the instance.

- A **worker token** acts as its registered machine and authorizes only the [worker protocol](../reference/worker-protocol.md). `api_tokens` stores its hash with the worker as its holder. The auth guard resolves that holder from the verified row, so the token prefix does not choose the actor. Worker authority comes from registry grants. Verification updates `last_used_at` at most once per minute. Worker authentication keeps no per-request counter.

Each personal or service-account token carries a scope fixed at mint time ([`TokenScope`](../../packages/db/src/access.ts)). The scope sets a maximum `role` and can limit the token to named `projects` or `environments`. The API applies that ceiling to every request. A token outside its listed projects or environments has no access, and a token inside them cannot exceed its maximum role. A token limited to environments cannot administer the whole project, so it cannot delete the project, grant project roles or change environment protection. A personal token without a narrowed scope follows its person's current rights, including later promotions. A narrowed personal token stays within its scope when its person gains rights. A service account token can reach only its account's project and can act at most as an `editor`. A refusal's `details.scope` holds the token's scope whenever that scope alone refuses the request, and `details.protectedEnvironment` names the environment whenever its protection alone refuses it, so a request that both limits refuse names both ([`decide`](../../packages/db/src/access.ts)).

Instance routes need an owner or admin whose credential is unlimited: a session or a token without a narrowed scope. A narrowed owner token acts as an admin of the projects in its scope and nothing more.

Minting, rotating and revoking personal or service-account tokens, and listing personal tokens, need a browser session, so no token mints a token. A project admin may list, create and delete the project's service accounts with a browser session or with a token whose scope reaches `admin` on that project, such as `swizzle service-accounts create`. The list shows each account's tokens without their values, and deleting an account deletes its tokens with it. The CLI's `swizzle service-accounts token create`, `rotate`, and `revoke` commands return `TOKEN_NEEDS_SIGN_IN`. The error directs a person to sign in to the dashboard and open `<project> > Service accounts > <account>`. Rotation (`POST /projects/<project>/service-accounts/<account>/tokens/<token>/rotation`) mints a token with the same name, scope and lifetime and revokes the old one in one transaction. An expired or revoked token cannot be rotated. A token id names that token even when another token is named like it. A revoked token stops on its next request.

`GET /auth/identity` tells any caller who it acts as and its token's scope. With `project` and `environment` it also answers the caller's role there. `swizzle whoami` prints it for the resolved profile, with the project and environment the profile pins. It names a person's token without limits `all your rights`, as the dashboard does, since an owner's or admin's instance role reaches past any project role; a limited token reads `at most <role>` with its projects and environments.

A service account's record shows who created it, and each of its tokens shows who minted it and when it was created, last used and revoked. The [audit](#the-audit-records-every-change) records what the account did, with the token it used, and the account's card on the **Service accounts** tab lists those events ([`project-service-accounts.tsx`](../../apps/web/src/routes/project-service-accounts.tsx)).

## The audit records every change

[`request-audit.ts`](../../apps/api/src/request-audit.ts) writes an audit event before handling a non-public write. It skips `GET`, `HEAD` and `OPTIONS` routes, and it also records approval-link decisions and event callbacks. Worker protocol routes skip the request hook. The worker registry records enrollment, renewal, revocation and refused scopes in the same table ([`worker-registry.ts`](../../packages/db/src/worker-registry.ts)). A worker heartbeat does not create an audit event.

An API request fails before it changes anything if the hook cannot write its event. The event records what the access check resolved and what the route adds, such as a reassignment reason, before the change. After the response, the API records its HTTP status. The API also records requests that the instance check or body schema rejects before the handler runs. If a request crashes before the response, its event has no HTTP status.

Trigger, deployment and timeout-grant writers add resource details to the active request event. If no request event exists, they write a new event. Scheduler events use a system actor. Worker protocol events use a worker actor. Worker creation and revocation use the requesting person's actor.

An event ([`audit_events`](../../packages/db/src/schema.ts)) records:

- The resource change, when present: trigger, deployment, timeout grant or worker details. Filtered histories and service-account activity read the same event.
- The actor kind and identity: person events record the user's id, role at the time, label, and token id, or `null` for a dashboard session. Service account events record the account id, label, and token id. A link decision records kind `link`, with no holder id. Worker events name the worker id and label. Background operations record kind `system`. Host commands such as owner recovery record kind `host`.
- API events record the method, route and path parameters except a link's token. Background events use the resource action.
- What the access check resolved: the project, the automation by id and slug, the run and the environment. An allowed write records its target. A refusal records its target only when the actor can already see it. A refused grant change also records the environment or automation slug it named. The audit leaves out details for a target the actor cannot see. A link request names the run its token points to.
- What the route adds, such as the reason, the old and the new assignee of a reassigned approval.

Only writing requests create events. A read creates none, including one that only an owner's or admin's instance role allowed. Neither does a deployment check (`POST /deployment-checks`, which `swizzle validate` and `swizzle apply --dry-run` send), because it changes nothing. An event marks a change that only the instance role allowed, without a grant on the project, as `privileged`.

The table has no foreign keys. An event outlives the automation, run, project and person it names, so a deleted automation's history stays readable. The automation's **Change history**, a worker's **History**, and a service account's **What it did** show filtered views of these events in words ([`words/audit.ts`](../../apps/web/src/lib/words/audit.ts)). The shared route policy in [`http-contract.ts`](../../packages/runtime/src/http-contract.ts) assigns each route its access rule and audit flag. `AuditedRoute` derives from that policy, so the dashboard must label every route the API records. Trigger receipts belong to run history, not **Change history**. `GET /audit` lists events newest first. It accepts filters for `automation` (slug or id), `worker`, `environment`, `actor` and `before` (an event id). An automation's **Change history** lists its changes and refused writes. Owners and admins read every event. A project admin reads events for that project. Other actors read only their own events ([`auditView`](../../packages/db/src/access.ts)). A token reads only its person's events within the token's projects and environments.

Resource histories return the same audit event envelope as `GET /audit`, including its actor, request, target, status and typed change. Each audited writing request has one event. A second attempt to insert an event or attach a resource change fails. Target facts keep their first known value ([`audit.ts`](../../packages/db/src/audit.ts), [`audit-tables.ts`](../../packages/db/src/audit-tables.ts)).

## Credentials need use and manage rights

A credential is a secret or a connection. Each belongs to one project and one environment. `?project=` names the project, and requests use `default` when the parameter is absent. Reading a credential's metadata needs viewer in that environment, so production credentials follow the production grant. Creating one needs editor there and gives its creator a `manage` grant on it. Two rights decide the rest ([`credentialRight`](../../packages/db/src/access.ts)):

| Right | Allows |
|---|---|
| `use` | Deploy a version that declares the credential, test a connection, and read who holds which right on it |
| `manage` | Also replace, re-authorize or delete it, grant or remove rights, and offer it to another project |

An instance owner or admin and an admin of the owning project manage every credential in it. Anyone else gets rights through grants to them or their teams. A `manage` grant counts as `use` when its holder lacks editor access in that environment. The API never returns a secret value or connection token. It checks the credential's identity again before a write, so a concurrent replacement cannot redirect that write to a different credential.

Anyone with `use` or `manage` can see each holder's effective right and its sources. The dashboard shows a direct grant, a team grant, or an instance or project admin role for each credential. Only a manager can add or remove a grant. Removing one grant leaves any right another grant or role gives. The [CLI reference](../reference/cli.md) lists the matching commands.

The **Credentials** page keeps the selected project in `?project=`. The Add secret and Connect an account forms start with that project. When the page shows all projects, each form starts with the first project the person can edit.

Grant `use` only when you trust the automation's code. The API keeps credential values write-only, but code that receives a value can send it to another system. `use` grants access to the value at run time; it does not make the code safe.

A deployment binds each secret and connection declared by its version, including the webhook signing secret, by credential id when it is published ([`findDeclaredCredentials`](../../packages/runtime/src/deployment-credentials.ts)). The platform checks `use` before the build and again before publishing. A permission revoked during a build therefore blocks that deploy. A missing credential also blocks the deploy, so set credentials before the first deploy.

Redeploying an unchanged version and rolling back need no `use` right. An operator can keep running a version an editor published. A rollback binds the credentials that its target version still declares.

A run receives only credentials bound to its deployment whose record or accepted share still exists. The platform checks the binding when it queues a run and before each attempt ([`boundCredentialsNamed`](../../packages/runtime/src/deployment-credentials.ts)). Deleting a credential removes that binding, even if someone creates another credential with the same name. The deployment cannot run again until someone sets the credential and deploys again. Replacing a secret's value keeps its binding. Moving an automation removes access to credentials in the project it left. Revoking a person's `use` right blocks their next deploy, while deployments they already published keep running.

A credential can serve another project through an approved share. Someone who manages the credential offers it, and an admin of the receiving project accepts the offer. If the same person administers both projects, the platform accepts the offer at once. The share applies only in the credential's environment. A deployment in the receiving project uses the shared credential only when that project has no credential with the same name. Its deployer needs `use` on the credential or admin access in the receiving project.

A project's **Credentials** tab shows incoming offers for its admins to accept or decline. It also lists credentials the viewer manages in that project, their outgoing shares, and controls to offer them to projects the viewer can see. The [CLI reference](../reference/cli.md) lists the matching commands.

Revoking a share removes the binding from every deployment that used it. The platform then blocks new and queued runs before it injects the credential.

## Backups stay private on the host

Backups can contain account records, encrypted credentials, and plaintext secrets in run output. `swizzle backup export` stages each export in a private directory, sets owner-only permissions on its whole tree, and publishes it to a new destination. See [back up and restore](../how-to/back-up-and-restore.md) for the export and restore steps.

## Every public route is a named exception

Every route needs a session or a bearer token, except the routes below. They are the routes marked `public` in [`ROUTE_ACCESS`](../../packages/runtime/src/http-contract.ts), plus `/ready` from loopback. Each exception has its own guard:

| Route | Why it is public | Guard |
|---|---|---|
| `GET /health` | Liveness | Answers only the service name, status and version |
| `GET /ready` | Readiness for the Compose health check | Only a direct request from loopback; from any other address it needs a credential |
| `OPTIONS` on any path | CORS preflight, which browsers send without credentials | Answers only CORS headers and runs no route |
| `GET /auth/status` | The dashboard asks whether to show setup or sign-in | Names the account only to the session that presents its cookie |
| `POST /auth/sign-up/email` | Setting up a fresh instance, or accepting an invitation | Before the first account, `SWIZZLE_SETUP_TOKEN` in `X-Swizzle-Setup-Token`; after it, a pending invitation's token in `X-Swizzle-Invitation-Token` for the body's email; sign-up budget; allowed `Origin` |
| `POST /auth/invitation` | The invitation page shows what the link offers | Answers only for a pending invitation's token |
| `POST /auth/request-password-reset`, `POST /auth/reset-password` | Recovering a forgotten password | Address budget, reset mail budget; the reset needs the mailed single-use token; allowed `Origin` |
| `POST /auth/sign-in/email` | Signing in | Durable sign-in budgets; allowed `Origin` |
| `POST /auth/two-factor/verify-totp`, `POST /auth/two-factor/verify-backup-code` | The second sign-in step, before a session exists | The challenge cookie from the password step, code budget; allowed `Origin` |
| `POST /auth/sign-out` | Signing out with an expired or revoked cookie | Ends only the presented session; allowed `Origin` |
| `POST /*` webhook ingress | Senders hold no Swizzle credential | Rate limit, optional HMAC signature |
| `GET /oauth/callback/:provider` | The provider redirects a browser without a token | Hashed single-use state ([connections](connections.md)) |
| `GET`, `POST /approvals/:token` | The approver has no account | Per-step capability token, rate limit ([approval and event links](approvals.md)) |
| `POST /events/:token` | A third-party system holds no Swizzle credential | Per-step capability token, rate limit, 64 KiB body ([approval and event links](approvals.md)) |

The [API reference](../reference/api.md) lists every route and marks the public ones.

The credentials these routes carry in the URL stay out of request logs. The logger writes the approval and event callback tokens and the OAuth callback's `code` and `state` as `[REDACTED]` ([`logger.ts`](../../packages/core/src/logger.ts)).

## Webhook ingress checks the client budget before the trigger

The rate limiter ([`webhook-ingress.ts`](../../apps/api/src/webhook-ingress.ts)) runs before the trigger lookup. It keeps one budget per client address, by default `60/min` (`SWIZZLE_WEBHOOK_INGRESS_RATE_LIMIT`). The budget covers every path and every environment, including unknown ones, so guessing paths or environments uses the same budget as flooding one webhook. Within the budget, an unknown environment answers the same opaque 404 as an unknown path. Approval links, event callbacks and OAuth callbacks use the same limiter ([`client-rate-limiter.ts`](../../apps/api/src/client-rate-limiter.ts)).

The limiter runs in the API process and tracks at most 10,000 client addresses. When it reaches that bound, it removes clients whose rate-limit window has passed. If the map is still full, it removes the client whose last allowed request is oldest. The limiter keys only by client address, so changing the environment or webhook path does not create another bucket for the same client. The limiter is not a distributed quota, and it does not replace DDoS protection in front of the host.

Production logging writes synchronously, to stdout by default or to `SWIZZLE_LOG_FILE` through a worker thread. File logging uses a 4 MB ring between the API and the worker. When the ring fills, the API waits for space instead of queuing more log lines in memory ([`logger.ts`](../../packages/core/src/logger.ts)). `SWIZZLE_TRUSTED_PROXY` decides which address counts as the client. Set it to the proxy's address or CIDR. Do not set it to `true` or a hop count. Fastify treats a hop count as an address, which would give every caller the same rate-limit budget.

A trigger that declares `signature` gets `HMAC-SHA256` verification of the raw body before the platform creates a run or a queue job. A failure answers the same opaque `404 WEBHOOK_NOT_AVAILABLE` as an unknown path, so a caller cannot tell a signed webhook from a missing one ([`webhook-ingress.ts`](../../apps/api/src/webhook-ingress.ts)). Only a signed-in person sees the cause: a `webhook_rejected` audit event with the reason `signature-invalid` ([`triggers.ts`](../../packages/runtime/src/triggers.ts)). Schemes that sign more than the body, such as a timestamp prefix, stay in automation code.

The signature check applies to public webhook ingress. `swizzle trigger` and **Run now** use `POST /automations/:automationName/runs`, which requires a session or token with run access. That identity authorizes the manual run, so the route skips the webhook signature check. The run therefore cannot pass as a delivery: its trigger type is `manual`, in the run row and in `SWIZZLE_TRIGGER_TYPE`, and it carries no webhook context, so the caller's headers never reach `SWIZZLE_WEBHOOK_HEADERS` ([`startManualRun`](../../packages/runtime/src/triggers.ts)). An operator may start runs but cannot make code that checks for `webhook` act on a forged event.

Automation code receives the request headers, except the three that carry Swizzle credentials: `authorization`, `proxy-authorization` and `cookie` ([`AUTOMATION_WEBHOOK_HEADER_DENYLIST`](../../packages/config/src/schema.ts)). Every other header is caller-controlled input.

## A run gets only what it declared

A deployed run starts with an empty environment. The API builds only what the attempt may hold: the declared secrets, the approval URL and the declared connection tokens ([`buildPlatformChildEnvironment`](../../packages/runtime/src/platform-secrets.ts)). It sends them only when the worker that owns the live lease starts the attempt. The executing machine adds a short allowlist of its own variables, such as `PATH` and `LANG` ([`platformBaseEnvironment`](../../packages/runtime/src/platform-secrets.ts)), and the runner adds the `SWIZZLE_*` run metadata. Database URLs, the encryption key and every other infrastructure variable stay outside. A run never receives a control-plane session or bearer token: it holds the credentials its deployment bound, not its deployer's authority.

The container is the second boundary ([`sandboxSpec`](../../packages/runtime/src/sandbox.ts)). It runs as an unprivileged user with a read-only root filesystem, all capabilities dropped, `no-new-privileges`, and limits on processes, open files, memory and CPU. `/tmp`, the home directory and declared `writable_dirs` are size-limited tmpfs mounts, so nothing a run writes outlives it.

[`containerLimitArguments`](../../packages/runtime/src/container-limits.ts) sets a PID limit of 128 per container and an open-file limit of 1024. It sets no per-user process limit (`--ulimit nproc`): every sandbox runs as the same user, and that limit counts the user's processes in all containers on the host, so one run holding processes would make every other run's fork fail. It also applies the memory and CPU values from `runtime.container`, which default to 512 MiB without swap and 1 CPU. The operator caps those values with `SWIZZLE_MAX_RUN_MEMORY_MB` (default `2048`) and `SWIZZLE_MAX_RUN_CPUS` (default `2`). A deploy above either cap fails with `RUNTIME_REQUIREMENTS_UNMET` and names the variable. The worker checks again before creating a container, so lowering a cap also stops older deployments above it. The maximum memory and CPU available to concurrent runs grows with `WORKER_CONCURRENCY`.

Every run gets a fresh container ([`claimSandbox`](../../packages/runtime/src/sandbox.ts)). The worker may start the container as a standby before a run needs it, so Docker does not create it on the run path. A standby has no run data or environment variables. Its create arguments match those of every run for the deployment. The worker passes secrets, metadata and inputs in the `docker exec` command that starts the automation ([`sandboxExecArguments`](../../packages/runtime/src/container-runner.ts)). A standby serves one run. Docker removes its container when the hold process exits, including after a run timeout. If the worker exits before Docker closes its sandbox hold processes, those sandboxes remain until the hold processes exit. At startup, the worker removes containers left by its previous container and by workers no longer running in the same Compose stack. The worker drains for 30 seconds on stop, and Compose gives it 45 seconds before it kills it ([`execution.yml`](../../infra/docker/execution.yml)).

The worker assembles each deployment's run image ([`ensureRunImage`](../../packages/runtime/src/run-image.ts)). It creates a container from the runner base, copies the source into it, runs any dependency install, and commits the container to an image. During installation, the container uses the sandbox user with all capabilities dropped and joins `runner-egress`. Dependency installers run code such as a PEP 517 build backend, so the install container gets the same process, open-file, memory, and CPU limits as a run. Both use [`containerLimitArguments`](../../packages/runtime/src/container-limits.ts). The install container's `/tmp` is a 1 GiB tmpfs, and its use counts against the memory limit.

When an automation has an install step, the worker samples the container's writable layer, which holds `/automation` and installed tools. `SWIZZLE_MAX_INSTALL_DISK_MB` sets the threshold in MiB and defaults to `4096`. The worker reads the layer size with `docker inspect --size` every second and kills the install step after a reading exceeds the threshold. It checks once more before committing the image. A successful install therefore stays under the threshold at its final check, but the layer can exceed it between readings. The run fails with `CONTAINER_BUILD_FAILED` and an error that names the limit when a check finds an excess.

This sampled limit is the strongest disk bound that works across the supported Docker setups. In six probe runs on the development host, a 256 MiB threshold and writes at about 1 GB/s produced layer peaks from 284 to 1,036 MiB. A 1 GiB burst finished before a check caught it twice. Each size reading walks the layer and took about 290 ms for 60,000 files, so checking more often would keep the daemon busy during ordinary installs. Docker's `--storage-opt size` does not work across all storage drivers. For example, containerd's overlayfs snapshotter on btrfs let a 120 MiB write pass a 50 MiB limit without an error. A tmpfs would impose a hard bound, but its pages count against the container's memory limit. A 300 MiB write to a 1 GiB tmpfs under a 128 MiB memory limit was killed. Install steps can still write more than the configured threshold before the worker detects and stops them.

Package downloads pass through the egress proxy. The worker commits the container instead of running `docker build`, so the broker does not need to allow Docker builds.

In Compose, the worker labels each run image with the stack's project name and prunes only images with that label. Stacks that share a Docker daemon keep separate run images ([`pruneRunImages`](../../packages/runtime/src/run-image.ts)).

Before assembling or reusing an image, the worker reports its tag through the authenticated worker API. PostgreSQL records the deployment, worker, environment and tag ([`createRunImageRetentionStore`](../../packages/db/src/run-image-retention.ts)). A prune keeps the worker's own latest reported image for every active deployment version in each environment. The version match preserves a cached image during an identical-source replacement, before the worker reports the new deployment. The worker asks for this keep set with its credential just before the pass, so its heartbeat's age plays no part. A revoked worker cannot ask, and PostgreSQL retains image records across worker restarts. Docker tags carry no retention state. An image also stays for ten minutes after assembly so its first run can start a sandbox from it.

The worker removes an unkept image when it exceeds `SWIZZLE_RUNNER_IMAGE_RETENTION_HOURS` or when keeping it would exceed the disk budget. The budget limits older, unkept images. The worker keeps active deployment images and images assembled in the last ten minutes, even when their combined size exceeds the budget. It never removes an active image to meet the budget or refuses a deploy or run because active images exceed it.

The worker asks Docker for each image's total size and shared size. Before keeping an image, pruning measures how many bytes it adds to the images already kept. Docker accounts for shared ancestor layers even when custom runner bases share only part of their ancestry. When images have the same base and private final layers, the worker reuses one base measurement and counts each private layer separately. It uses this accounting for active, fresh, and retained inactive images. An interrupted commit with no tag receives a stable tag derived from its image ID so Docker can include it in the same accounting. Normal pruning removes that tag with the image. The next heartbeat reports the active images' combined size and the disk budget. When active images alone exceed the budget, **Settings > Workers**, the Overview, and `swizzle worker list` show a warning with the worker name, measured total, and budget. Remove deployments the worker serves to reduce the total. To keep them, raise `SWIZZLE_RUNNER_IMAGE_DISK_MB` on the worker and restart it. Docker may refuse to remove an image that a running container uses. A later prune pass can remove that image.

The worker prunes after it prepares a deployment or stops tracking an inactive deployment, and every fifteen minutes. Before pruning, the worker completes preparation for every active deployment in the poll, so it has reported each needed image tag; preparation and pruning take turns in one loop, so the process records no tag during its own pass. No lock spans the pass. Worker replicas that share one credential and one Docker daemon can race: a replica that reuses an old cached image for a new deployment while another replica prunes may lose that image, and the deployment's first run assembles it again. Docker refuses to remove an image a container uses. A failed keep read skips pruning. Trusted local container runs use a separate `local-` stack namespace for assembly, sandboxes and pruning.

With `permissions.network: false`, the container has no network. By default the run may use the network: the container joins the internal `runner-egress` network, and its only way out is the egress proxy ([`squid.conf`](../../infra/docker/squid.conf)). The proxy allows ports 80, 443, 465, 587, 993 and 995 and refuses private, loopback, link-local, carrier-grade NAT, multicast and documentation ranges for IPv4 and IPv6. That stops a run from reaching PostgreSQL, Valkey, the cloud metadata endpoint or the operator's LAN.

Workers have one named service exception. An owner or admin grants a worker `local-llm`, and an automation requests it through `runtime.permissions.services`. The proxy permits only `local-llm-inference:8080`, the gateway's inference listener. Ordinary runs have no gateway credential and receive 403 there. The gateway control listener binds a separate interface on `runner-control` and authenticates the worker with a host-specific control token.

The worker registers a random token for each attempt and injects only that token and the inference URL. The gateway stores its hash, expires it after 30 seconds without renewal, and revokes it when the attempt ends or loses its execution lease. Revocation aborts active inference. Renewing an attempt never refills its request quota. The runner redacts the exact attempt token from its output before streaming or reporting it.

The gateway sends only text chat completions to one operator-configured literal IP address and port. It selects the model, strips run-supplied headers and rejects model overrides, tools, files, management paths and redirects. Request and response sizes, request duration, concurrent requests, requests per attempt and output tokens are bounded. An unavailable service prevents placement of runs requiring it. [Configure the service](../how-to/add-a-remote-worker.md#call-a-local-llm-on-this-worker) on its host. GPU devices remain denied by the Docker broker. All other private destinations and ports retain the proxy's denial.

In the Compose stack, the API and worker have no direct route to the internet. Their outbound HTTP clients use a separate control egress proxy on the internal `control-egress` network ([`http-egress.ts`](../../packages/core/src/http-egress.ts)). The proxy applies the runner proxy's destination restrictions, with exact hostname and port exceptions for `SWIZZLE_ARTIFACT_S3_ENDPOINT`, `OTEL_EXPORTER_OTLP_ENDPOINT` and, on a remote worker, `SWIZZLE_WORKER_API_URL` ([`control-egress.mjs`](../../infra/docker/control-egress.mjs)). Those endpoints may use a LAN address or the Docker host at any port. `host.docker.internal` names the Docker host from the control proxy. Sandboxed runs cannot reach the control proxy and get none of its exceptions. The local worker reaches the private worker listener directly, Docker through the broker, and tracing through the configured control proxy. It has no PostgreSQL, Valkey, encryption key, artifact mount or storage credentials. Remote workers initiate HTTPS requests and receive only the inputs, source, declared secrets and access tokens of their accepted execution; a request for another attempt's source or secrets gets HTTP 409 ([`dispatch-service.ts`](../../packages/runtime/src/dispatch-service.ts)). The local worker serves every project and environment of the instance. A remote worker serves only the projects, environments and groups an owner or admin granted it. The scheduler and Caddy use the outbound network directly.

An API check runs in the same sandbox as a run of its deployment, with the same image, egress proxy and limits. It always receives the automation's connection tokens. By default, it also receives all declared secrets. Set `api_check.secrets` to give it only a subset of those secrets. This setting does not limit its connection tokens.

The platform cannot make a check read-only. HTTPS passes the proxy as `CONNECT`, so the proxy sees only host and port. Nothing stops the check from sending a `POST`. Read-only is a convention that the scaffolded stub teaches. If the provider offers a read-only key, put it in `api_check.secrets`.

### Docker lifecycle limits

[`DockerScope`](../../packages/runtime/src/docker-cli.ts) owns Docker CLI processes and, when named, their containers. Image inspection, container create/start/stop, removal, and each command of an image prune pass have a five-second deadline. Copy and commit have a sixty-second deadline because they move source files and image layers. The attached install command uses the assembly owner's ten-minute deadline. When a command expires, the worker kills the CLI process group on POSIX or the CLI process on Windows, closes the output pipes, waits for the CLI to exit, and reports `DOCKER_CONTROL_TIMEOUT`.

The run's `docker exec` has no deadline of its own: the run's timeout bounds it. When the run times out, is cancelled, or passes the output limit, the worker stops the sandbox with `docker stop`, falling back to `docker kill`. Once those commands return, the exec has one more second to end. If the daemon no longer answers the exec, the worker then kills the exec CLI's process group and closes its pipes. Stop and kill each have a five-second deadline, so a run ends at most about eleven seconds after its timeout, even when the daemon stops answering.

An image inspection timeout fails preparation or the run instead of making the worker treat the image as missing. A standby creation failure reaches the run instead of causing a second create attempt. If a size inspection times out during installation, the assembly owner stops the attached install and removes its container.

Container removal makes at most three attempts, each with a five-second deadline and a one-second pause between attempts. Cleanup can take up to seventeen seconds after a failed create or assembly. A sandbox create may finish in Docker after a timeout and an initial removal attempt. Preparation and prune passes remove Created `swizzle-run-*` containers labelled for this stack and worker process when no active Docker scope owns them. They leave running containers, other worker processes, and image assembly containers alone. If Docker cannot answer, cleanup remains best effort. `just stack-down` stops the worker, removes every container labelled for the stack, removes the Compose stack and its volumes, then removes the images labelled for the stack by ID. It does not run `docker image prune`, which would delete the containerd leases of every image import and commit in flight on the daemon, including another worker's run image assembly.

Runs for the same image share one assembly, so cancelling one run leaves it available to the others. Worker shutdown closes all Docker owners before waiting for deployment preparation. The worker retries an ordinary Docker command failure once after cleanup. It does not retry a deadline, an unavailable runtime, or a failed install step in place. A Docker failure that remains, or a deadline, fails the attempt with `CONTAINER_RUNTIME_UNAVAILABLE` or `DOCKER_CONTROL_TIMEOUT`, and the run retries it within its retry budget. A failed install step is the automation's own: it fails the run with `CONTAINER_BUILD_FAILED` and no retry. The step counts as failed when its container exited with a non-zero code, ran past the assembly deadline, or wrote past the install disk limit. When `docker start --attach` fails or the Docker CLI cannot start, and the container did not exit non-zero, Docker failed and the run retries.

## The worker reaches Docker only through the broker

The Docker socket grants control over the host. A container create request can cross the sandbox boundary if it asks for privileged mode or a host mount. Only `docker-broker` mounts the socket, and the worker reaches it over the internal `runner-control` network ([`compose.yml`](../../infra/docker/compose.yml)). The broker checks request paths and bodies because an HTTP method allowlist alone cannot restrict container options ([`policy.ts`](../../apps/docker-broker/src/policy.ts)).

The broker accepts container creates only when they match a sandbox or image assembly. Each create must use the sandbox user, drop all capabilities, set `no-new-privileges`, join `none` or `runner-egress`, and carry the stack label. Both shapes must carry the limits `containerLimitArguments` sets: memory and CPUs set and within `SWIZZLE_MAX_RUN_MEMORY_MB` and `SWIZZLE_MAX_RUN_CPUS`, which the broker reads like the worker, swap equal to memory, a PID limit of 128, and an open-file limit of 1024. Docker reads a missing or zero limit as unlimited, so the broker refuses it. The broker rejects privileged mode, host mounts, devices, host namespaces, and fields the worker does not send. An exec cannot enable privileges or switch users.

For existing containers and images, the broker checks the `swizzle.stack=<project>` label before acting. It permits image tags only in `docker.io/library/swizzle-run`. The worker prunes by removing tags and images one at a time, each checked for the stack label, so the policy has no route for Docker's image prune. The worker can inspect images and pull images. It can list containers only by its stack's label or by the label Compose puts on the stack's worker containers. Docker builds, volume and network operations, plugins, and every route absent from the policy are refused. The broker bounds request headers and create or exec bodies to 1 MiB. Image disk accounting sends selected image references in the query, so its headers can exceed Node's default 16 KiB limit. A new worker Docker call fails until the broker policy allows it.

Each request owns what the broker asks of the daemon for it ([`broker.ts`](../../apps/docker-broker/src/broker.ts)). When the worker's Docker CLI disconnects because its deadline passed or it was killed, the broker closes the ownership lookups and the forwarded request for that call. Before a raw-stream call is upgraded, the broker reads and holds what the client sends, so it also sees that client leave. An ownership lookup that the daemon does not answer within five seconds fails with `504`. A forwarded call has no broker deadline, because a wait or an attach lasts as long as its container.

A compromised worker can pull images and run code in its stack's sandbox and image assembly containers. It cannot use Docker to create a privileged container or mount a host directory.

A trusted local `swizzle run` uses a host process instead of a container. That mode is for authoring on your own machine, not an isolation boundary.

## Run output hides injected credentials

If a run prints an injected secret or connection token, the output redactor replaces its exact value with `[REDACTED]` ([`createRunOutputRedactor`](../../packages/runtime/src/output-redaction.ts)). It also replaces approval and event link tokens by matching their shape, because each token grants one decision or event ([approval and event links](approvals.md)). The API applies this redaction to stdout and stderr before it stores or streams output. It also applies it to parsed results, failure messages, causes, and stacks. The streaming redactor holds back a chunk's unfinished suffix, so a token split across writes stays hidden. It merges overlapping matches before replacing them.

Redaction does not contain malicious automation code. Code can encode a credential before printing it or send it over the network. Local `swizzle run` output is not redacted. The API stores state, step values, child payloads, and approval details as the run wrote them, so worker routes can return the original values for replay. Responses to people and API tokens replace link tokens in serialized JSON text with `[REDACTED]`. This leaves the JSON representation produced by serialization unchanged except for the token characters. The approval page also redacts links in its details. These response filters hide link capabilities without changing the stored values or the stateless wait-link design.



## The dashboard treats deployed content as untrusted

A token can deploy when its person has editor access in the target environment. A bundle or run may carry hostile content. The dashboard renders run output, logs, payloads, step values, flow labels and lane labels as text. Mermaid parses `flow.mermaid` at its `strict` security level. For flowcharts, the dashboard draws the parsed data with its own elements ([`flow-source.ts`](../../apps/web/src/lib/flow-source.ts), [`track.tsx`](../../apps/web/src/components/track.tsx)). For other Mermaid diagrams, it sanitizes Mermaid's SVG with DOMPurify ([`flow-diagram.tsx`](../../apps/web/src/components/flow-diagram.tsx)). The Play tab shows the deployed entrypoint as text ([`automation-play.tsx`](../../apps/web/src/components/automation-play.tsx)), never as HTML. The README sanitizer removes `style`, `class` and `id` attributes so README content cannot position itself over the dashboard or reuse dashboard styles. Paint containment clips README content to its article. These rules stop a README from covering the dashboard with a fake sign-in prompt.

Settings › Agent access and a project's Service accounts tab keep a newly created or rotated token in component state ([`settings/agent-access.tsx`](../../apps/web/src/routes/settings/agent-access.tsx), [`project-service-accounts.tsx`](../../apps/web/src/routes/project-service-accounts.tsx)). Done clears it, and the page clears it on `pagehide` before the browser can put the page in its back/forward cache. If token creation finishes after the page has been hidden, the page does not show the token.

Secret values use a text field with attributes that ask password managers to ignore it ([`SecretInput`](../../apps/web/src/components/secret-input.tsx), which edits the value in [`secret-edit.ts`](../../apps/web/src/lib/secret-edit.ts)). Password managers can save password fields regardless of their autocomplete setting. The text field holds mask characters while component state holds the value, so ordinary edits keep the value out of the accessibility tree. Screen readers and browser-driving agents read that tree. An input method temporarily places composed text in the field, where CSS masks it until composition ends. Password managers vary, so these attributes cannot guarantee that every manager ignores the field.

## Caddy preserves API page policies

In production, Caddy sends the dashboard a Content Security Policy with `script-src 'self'` and `frame-ancestors 'none'` ([Caddyfile](../../infra/docker/Caddyfile)). The API sets a policy on every response, and Caddy preserves it on the API origin, links origin, and dashboard's `/api/*` route. The approval page's policy allows its inline script by hash, so the script runs through each route.

The Vite dev server sends `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every response, including the 304 that revalidates a cached page ([`vite.config.ts`](../../apps/web/vite.config.ts)). It does not send the full policy because that policy blocks Vite's inline HMR preamble. The framing headers also matter in development: browsers treat different ports on the same host as the same site, and a matching session cookie can reach a page that frames the dashboard.

## Production refuses an unsafe configuration

With `NODE_ENV=production`, the API checks its configuration at startup and exits instead of serving an unsafe one ([`assertPublicSecurityConfiguration`](../../apps/api/src/security-config.ts)). It refuses to start:

- with `SWIZZLE_TRUSTED_PROXY=true`;
- with a setup token shorter than 32 bytes on a non-loopback bind;
- on a non-loopback bind without `SWIZZLE_CONTROL_EGRESS_PROXY`, or with one that is not a plain `http://` URL without credentials ([`parseEgressProxyUrl`](../../packages/core/src/http-egress.ts), the rule `SWIZZLE_RUNNER_EGRESS_PROXY` follows too);
- with a non-local origin, including `SWIZZLE_LINK_URL`, that is not HTTPS;
- with secure cookies turned off for a public HTTPS origin.

`swizzle security audit` reports the same posture on a running instance and exits non-zero when a critical check fails ([`security-audit.ts`](../../apps/api/src/security-audit.ts)).
