# Measure speed and resource use

Run `just perf` to measure API routes, run lifecycles, service resource use, and dashboard pages on the packaged stack behind Caddy. The recipe creates a throwaway Compose project on free ports and seeds it with the same data each time. After the run, it removes the project's labelled containers, networks, volumes, and images. It also removes resources left by a failed start. Each run gets its own project, so concurrent runs do not share a stack. At startup, `just perf` removes old `swizzle-smoke-*` and `swizzle-perf-*` projects when their recorded process identity no longer matches. It removes their temporary directories too. See [the local stack guide](run-a-local-stack.md) for how cleanup checks process ownership.

Cleanup deletes image IDs selected by project labels, so parallel runs do not share Docker's global image-prune operation.

## Tell whether a change made things faster

On your branch, run `just perf --against <git ref>`, for example `just perf --against main`.

The recipe unpacks the ref's committed tree into a temporary directory and boots a second stack beside the stack from your checkout. It measures both stacks in each round and alternates their order. This reduces the effect of host load on the delta. Your checkout's measuring code and CLI drive both stacks. The recipe removes both stacks and the temporary directory on exit.

Instead of the summary, the run prints one line per metric: the base and head medians, the delta, the spread and a verdict. The spread is the larger min-max range of the five rounds of either side, and at least the resolution of the metric's unit, such as 1 MiB or one long task. A delta inside it reads `same`, because the rounds already vary that much. For a service's memory, the spread is also at least the memory the kernel handed either side's service in huge pages since it started. Where the kernel's transparent huge pages are set to `always`, the host's memory at the moment a service starts decides whether it gets them, so an idle valkey holds between 3 and 12 MiB from one start to the next with the same code. `BETTER` and `WORSE` mean the delta left the spread in the direction the metric improves or degrades.

For a quick look against a result you already have, run `just perf --base <result.json>`. That base ran at another time, so a change in the host's load between the two runs moves the delta too, and the spread of the rounds does not cover it. Compare the load and stall share in the two headers before you trust such a delta. The comparison warns when the host differs. Each side records worker replicas, `WORKER_CONCURRENCY`, service resource limits and selected nonsecret runtime settings from its own resolved Compose configuration. When the profile or resolved stack settings differ, the comparison lists the differences and judges no metric. It exits nonzero unless you pass `--experiment <label>`. Measure the base again with your checkout, for example with `--against`. For an intentional configuration experiment, add `--experiment <label>`. The label appears in the result and header. When scenarios differ, the command exits successfully but still gives no regression verdicts.

Results stay under `git rev-parse --git-path swizzle-perf` of the worktree that ran them, so removing a worktree removes its results. A base measured with `--against` lands beside the head result, with `-base` at the end of its name. Copy a result you want to keep. `--base` validates the current result format before booting a stack. Malformed files, invalid metric values and files without scenario metadata fail with a usage error.

## Measure one half

`just perf api` measures only the backend, and `just perf web` measures only the dashboard. A base from a full run compares with either half on the metrics both hold. Below the table, the comparison names the groups whose metrics only one side holds, and each metric whose unit or direction changed between base and head. It judges none of those. When base and head share no metric, it says so in place of the table.

## Read the numbers

Every cell of the summary is `median [min-max]` of five rounds. A warmup precedes the rounds and is not recorded. Each round visits every route, page and interaction once, in turn, so a slow moment of the machine lands in one round of each instead of in every round of one.

The seed is four webhook examples and twelve succeeded runs of `hello-webhook`, deployed and triggered through the API before anything is measured. The pages are measured first and the routes second, so both read only the seed. The run lifecycle comes last because it adds runs. Each of its rounds first deploys a new version of `hello-webhook`, a copy of the example with a changed source file, and measures its first run. The rest of the round runs that version. Perf waits for worker preparation before this first-run sample; a run triggered just after `swizzle apply` may still wait for the remaining image preparation ([deployments and rollback](../explanation/deployments-and-rollback.md#a-worker-prepares-a-deployment-before-its-first-run)).

| Table | What a cell is |
|---|---|
| `GET <route>` | Latency percentiles and throughput of 200 requests per round from 8 concurrent clients through Caddy with the owner's session cookie, as the dashboard sends them, and the count of non-2xx answers. `/health` is the floor: Caddy and Fastify without a database. The `(token)` row sends the owner's agent token instead, as the CLI does. Token requests update the last-use time at most once per minute per token. The row includes the cost when a request writes that timestamp. |
| `first run hello-webhook` | The first run of the round's new version. `prepared` is the time from `swizzle apply` returning until every worker replica logs `Prepared deployment.` after assembling the run image and any standby sandbox. Perf triggers the run after that. A stack whose worker does not prepare deployments has no `prepared` cell, and its first run waits for the image. If a worker logs a failed preparation, perf writes the missing worker count and available error to stderr, then records no `prepared` cell. If preparation has no result after 60 seconds, perf records no `prepared` cell. The other cells are those of the next table, for this one run. |
| `run hello-webhook` | Ten runs one after another, each triggered with the owner's agent token. `queued` is `startedAt - queuedAt` and `execute` is `finishedAt - startedAt`, both from the run record, so polling adds nothing. The worker records where `execute` went on the run's attempt: `image` assembling the run image, 0 when it existed; `sandbox` claiming the sandbox, a standby or a new container; `process` staging the inputs and running the automation; `other` the rest, such as loading the deployment, secrets and state, and storing the result. `standby` counts the runs that found a standby. A stack without these records shows only `queued` and `execute`. With ten runs per round, `total p95` and `total p99` are the slowest run. |
| `burst of 10 runs` | Ten runs triggered at once: runs per second from the first `queuedAt` to the last `finishedAt`, and how the time splits between waiting for a worker slot and running. The header names the effective worker replicas and concurrency; shell overrides such as `WORKER_CONCURRENCY=4 just perf api` become part of the saved scenario. |
| `service <name>` | CPU seconds and peak resident memory (anonymous plus shared memory, without page cache) of each service, during the route, deploy and run phases of one round, from the Docker Engine API. A service with several replicas reports their sum: CPU seconds added up, and the peak of the replicas' summed memory. The automation containers the worker starts are not counted. A failed stats read cancels the workload and removes the stack. Each stats request has a five-second deadline and a 1 MiB response limit. Each route load, run trigger, run wait and run detail request has a 60-second deadline, so an API response that stalls fails the round with a timeout error and removes the stack too. |
| `phase duration` | The wall time of the route, deploy and run phases of one round. |
| `page <path>` | A cold load in Chromium at 4x CPU slowdown, 40 ms latency and 10 Mbit/s down: FCP, LCP, total blocking time after FCP, CLS, the long-task count, and the JS and CSS bytes transferred. The page counts as loaded when the network has been quiet for 500 ms, plus one second. |
| `interaction <name>` | From the click until the page settles again: the longest event duration (INP), blocking time, long tasks, the 95th percentile of the frame interval and the count of frames longer than 50 ms. |

The header names the commit, the machine, its load average before and after, and on Linux the share of measured time when a task on the host waited for a CPU or IO. Other host work can raise these measures and widen the results. Database writes and container starts wait on the disk and on Docker, so the run lifecycle and the `(token)` row move with the IO share. When base and head show different shares, a delta in those rows can come from the machine rather than the commit.

## Find what limits a number

- Compare a route with `/health` and `/auth/status`. `/auth/status` adds the session lookup, and the difference to a route is the work behind it: its database reads and the serialization of the answer.
- Divide a service's CPU seconds by the `phase duration` of the same phase. A service near one CPU second per second is single-threaded and saturated, as the Node api is when its routes stop scaling with more clients.
- For a slow run, compare `queued` with `execute`. A long queue means the worker had no free slot. A long execution means the run or its container start took the time.
- For one request's path through the services, use traces, as [Enable tracing](enable-tracing.md) describes.

`just perf` sets no budgets, and the gate does not run it.
